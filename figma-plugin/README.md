# @dtpr/figma-plugin

Figma plugin that generates a DTPR icon **component library** from the
public API at `api.dtpr.io`.

Run it once in an empty Figma file, publish the result as a Team
Library, and every designer gets the full DTPR icon set in their Assets
panel — no plugin install required on their end.

## Why a plugin at all

Figma's REST API is read-only for file content; there is no endpoint
that writes nodes into a document. Anything that *creates* layers has
to run inside Figma as a plugin. So the library can't be generated by a
build script — this is the vehicle.

The DTPR API cooperates well with it: every route is public, sends
`Access-Control-Allow-Origin: *` (see `api/src/middleware/cors.ts`), and
serves composed icons as ready-made SVG strings that
`figma.createNodeFromSvg()` accepts directly.

## What it produces

For `ai@2026-08-24-beta`: **137 elements across 14 categories, 468
icons**.

```
Page  "DTPR Icons — ai@2026-08-24-beta"
 └ Frame "purpose"                      one section per category, in schema order
    ├ Text  "Purpose"                   category name + description
    ├ ComponentSet "purpose/accessibility"
    │   ├ Component "Theme=light"
    │   │   └ Frame "icon"  → "shape" (category shape) + "symbol" (element glyph)
    │   └ Component "Theme=dark"
    └ Text  "Accessibility"             optional caption
```

Details worth knowing:

- **Variants map to two Figma axes.** The API exposes icons as flat
  tokens (`default`, `dark`, `vendor`, `vendor.dark`); those are really
  a *context* axis and a *theme* axis, so the plugin splits them back
  apart and builds `Context=vendor, Theme=dark` component sets. Only
  the axis that actually varies is named — 104 elements have just
  light/dark and get a plain `Theme=…` property.
- **Each component carries its element description** in Figma's
  `description` field, so the plain-language meaning shows up in the
  Assets panel and instance inspector.
- **Each node is stamped** with `setPluginData('dtpr', …)` recording
  the element id, schema version, and content hash. That's what a
  future "re-sync this file to a newer schema version" command would
  key off.

## Install (local development)

```bash
pnpm install
pnpm --filter ./figma-plugin build
```

Then in the Figma **desktop** app: *Plugins → Development → Import
plugin from manifest…* and pick `figma-plugin/manifest.json`.

`pnpm --filter ./figma-plugin dev` rebuilds on change; use *Plugins →
Development → Hot reload plugin* in Figma to pick changes up.

## Publishing

`manifest.json` deliberately has no `id` field. Figma assigns one the
first time you publish — add it to the manifest then and commit it.

Distribution options, in rough order of effort:

| Route | Requires | Who can use it |
| --- | --- | --- |
| Local dev plugin | nothing | whoever imports the manifest |
| Private org plugin | Figma Organization or Enterprise plan | your org only |
| Figma Community | public listing + review | anyone |

For most teams the answer is: run the plugin once yourself, then
publish the **generated file** as a Team Library. Consumers never touch
the plugin.

## Rate limiting

This is the one thing that will bite you if you change the fetch logic.

`RL_READ` in `api/wrangler.jsonc` allows **300 requests per minute**, and
a full build is **468 icon requests** plus metadata. The plugin
therefore:

- sends `DTPR-Client: dtpr-figma-plugin/0.1.0` so the API buckets it
  separately from the shared anonymous pool
  (`api/src/middleware/rate-limit.ts`),
- paces itself with a sliding-window limiter set 20 requests below the
  ceiling,
- honours `Retry-After` on a 429 and backs off exponentially on 5xx,
- lets a single failed icon drop just that variant rather than the
  whole element.

A full run takes roughly two minutes. The **Default context only** and
**Light theme only** options cut it to 137–274 requests when you just
need a quick refresh.

## Layout

```
src/
  api.ts        URL builders + response types           (pure)
  variants.ts   variant token ⇄ {context, theme} axes   (pure)
  layout.ts     wrapping grid math                      (pure)
  messages.ts   typed UI ⇄ sandbox protocol
  code.ts       plugin sandbox — everything that touches the document
  ui/
    ui.html     panel markup; `%BUNDLE%` is replaced at build time
    ui.ts       panel logic + all network calls
    net.ts      rate limiter, retry, bounded-concurrency map
```

The UI/sandbox split is forced by Figma: `fetch` only exists in the UI
iframe (declared under `networkAccess` in the manifest), while node
creation only exists in the sandbox. So the UI does all the network
work and streams icons across in batches of 24; the sandbox reassembles
them by element id and builds.

Layout uses absolute positioning with a pure, unit-tested packer rather
than Figma auto-layout — wrap behaviour depends on resize/sizing-mode
ordering that's awkward to get right without running in Figma, and the
output is a static generated artboard either way.

```bash
pnpm --filter ./figma-plugin test       # 22 tests over the pure modules
pnpm --filter ./figma-plugin typecheck
```

## Verification status

The pure modules and the network layer are tested and were exercised
against the live API: 14 categories, 137 elements over 1 page, 468 icon
tasks, 0 unparseable variant tokens, 137 collision-free component
names, and sample icons — including context+dark variants — returning
the expected `<path>` + `<g>` structure.

The document-building path in `code.ts` has **not** been run inside
Figma. Import it locally and generate once before publishing anything.
